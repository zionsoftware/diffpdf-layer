### フォント・順序・集計の調査

B1はAPの展開後バイト列・文字・明示座標が同じでも、AP資源の埋め込みMSPMinchoのサブセット名・データとCourierNewの字形範囲（FirstChar 32→65）が変わっていた。作成者の差を内容判定へ混ぜず、フォント資源の差を既存のfont_changesへ保持してFと判定した。B2は文字のない矩形で/Tだけの内容分離を別途確認している。

D1では文字列と注釈Rectを維持した操作でも、AP内の文字「の」の後のTdが11.388→12となり、後続文字の明示位置が0.612ptずれた。RichTextも削除されている。この実出力をフォントだけの一致へ変更すると、実際の配置差を見逃す。D2はMSゴシック→MS明朝で同じTd列を維持し、Fを実機で確認できた。未知の文字マッピングを推測して一致にする変更は行っていない。

Fは/Annotsの順序差を/NM（このサンプルで一意）による照合で確認した。重なる矩形2個のRectも同じで、内容と重複数を維持した前後移動である。注釈の内部AP命令順を並べ替えた試験や、ページ本文の任意の命令交換を実機で確認した意味ではない。

各比較で、エンジンの作成者集計をPDF直読の/T別件数・未設定件数と照合する。内容不一致・F・追加/削除でも双方の集計が完全であることを確認する。個別注釈のユーザー変更対応は表示せず、PDFごと・グループごとの構成として扱う。公開記録には実名を転記しない。TXT・CSV・JSONを新規保存し、schema_version=3の読み戻し、判定・件数の整合、GUIとTXT共通の詳細表示、廃止した合成順序行の不在も自動検査する。今回の比較ツールGUIの実画面による全行の確認は行っていない。

| one-annotations-b の自己比較 | 一致 | 一致 | 一致 | 一致 |
| one-annotations-a → one-annotations-b | 一致 | 不一致 | 不一致 | 一致 |
| two-resaved → two-unassigned | 一致 | 不一致 | 対象なし | 対象なし |

`one-annotations-a/b` は検証者Aの矢印・矩形・日本語タイプライター注釈を含む。Bでは日本語注釈の末尾AをBへ変更した。Editorの評価版保存により、各ページのウォーターマークBDCが4個から6個に増え、1ページ目の本文命令が637個から649個へ増えた。未加工のまま、文字変更を検証者A、DEMO増加をレイヤーなしとして検出し、PDF本体と未変更の検証者Bは一致した。重なり順の判定や矩形の交差検査は行わない。

原本2ファイルと `two-unassigned` の自己比較も全グループが一致する。2upに追加した未所属の矩形は異常ではなく、レイヤーなしの差として検出される。

## 注釈の作成者名（PDF記録値）

未加工の `one-annotations-a/b` と `two-unassigned` を、pypdfによる直接の注釈辞書走査と独立に照合した。名前の実値は公開文書に転載せず、Git管理外のローカルレポートに保持する。

| グループ | one-annotations-a | one-annotations-b | 集計 |
|---|---|---|---|
| レイヤーなし | 名前なし、未設定16件 | 名前なし、未設定24件 | 完了。構成変更あり |
| 検証者A | 1種類の記録名、3件 | 同じ記録名、3件 | 完了。構成変更なし |
| 検証者B | 注釈なし | 注釈なし | 完了。構成変更なし |

検証者Aの内容不一致と作成者名構成の変更なしを同時に出力する。自己比較は内容一致・構成変更なしとなる。GUIと同じデータからTXT / CSV / JSONを生成し、JSONの読み戻しでも集計と内容判定が保持される。再解析前後でローカルの原本・コピー・保存出力・前回加工コピー計13個のPDFのSHA256が不変であることを確認した。

注釈に記録された作成者名は、内容の同一性判定から除外し、参考情報としてグループごとに表示する。作成者名の変更だけでは不一致としない。作成者名は実際の操作ユーザーや最終編集者を証明する情報ではない。

## 加工コピーとの区別

前回の `*-no-demo-links.pdf` は、pypdfでLink注釈だけを取り除いた別ファイルであり、Editorの未加工出力ではない。DEMO描画、OCG、矢印・矩形・日本語注釈は残っている。新仕様でも別の検証ケースとして比較し、日本語変更が検証者A、DEMO描画増加がレイヤーなしへ現れ、PDF本体・検証者Bが一致することを確認する。

今回の重点検証は未加工の方である。新仕様では未加工出力からLinkを除く必要はない。

## フォント変更・DEMOだけの変更の根拠

前フェーズにはなかった条件を、再開後の未加工実出力で追加した。B2・H通常保存で/Tだけの変更、D2でフォントだけの変更、B1で作成者変更とフォント資源の再サブセット化、Fで重なる注釈の/Annots順序変更を確認した。空レイヤー追加削除・最適化保存では、既存A/Bの注釈内容を変えずにDEMO/URI Linkが増え、Uだけが不一致となる条件も確認した。詳細は冒頭の表を参照する。

生成PDFでは、さらにファミリー、埋め込みデータ、CIDコード変更、AP、DA、RC、DS、複数フォントと反例、独立したページ描画・状態継承・複雑な未対応構造を検査する。生成条件をすべてEditorで実機確認した意味ではない。

過去の`GetCursorPos`等の失敗後、利用者による再ログインで操作を再開できた。直近の線色パレットの画面取得問題と回復方法も冒頭に記録した。

## 再実行

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_xchange_integration.py tests/test_xchange_resumed.py -q
```

サンプルが存在すれば従来16ケースと再開後24ケースを検査する。PDFやローカル結果はGitへ登録しない。サンプルがない環境では理由を付けてスキップする。通常の生成データテストは実行できる。

本プログラムは、PDF本体・レイヤーなし・各OCGレイヤーの内容を比較する。オブジェクトの重なり順や視認性は判定しない。チェックマーク・注記の視認性や妥当性は、担当者・確認者・審査者が目視で確認する。

Popup / IRT、Editorによる平坦化、増分保存、最適化の別設定、大規模図面、Windows各版・DPI・オフライン環境は追加検証が必要。所属移動は実機で確認したが、平坦化は生成データの検査と区別する。
