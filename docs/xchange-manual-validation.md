# PDF-XChange Editorで残る実機検証の手順

対象: PDF-XChange Editor 11.1.0.0、Python 3.14.8、pypdf 6.20.1。2026-10-16の検証で変更なし保存を実施した後、Computer Useの入力エラーで中断したケースを再開するための手順。

## 原本と基準の準備

1. `tests/mixed_1up_8pt.pdf`、`tests/mixed_2up_8pt.pdf` と既存の `output/xchange-validation` 内のファイルは編集しない。新しいサブフォルダーを作り、コピーを置く。
2. 今回のコピーは `output/xchange-validation/phase-20261016-175704` にある。`a-input.pdf` と `a-resaved.pdf` は内容が同一で、検証者Aに矢印・矩形・日本語タイプライター注釈、検証者Bに空のレイヤーがある。別のフォルダーへコピーして作業してもよい。
3. Editorに `a-resaved*` が残っている場合、作成者名だけを変更した未保存状態の可能性がある。続行するなら、まず **新しい名前** `b-author.pdf` で保存する。基準の `a-resaved.pdf` を上書きしない。状態が分からなければ、未保存変更を破棄したうえでディスク上のコピーを開き直す。
4. 以後の各ケースは、同じ基準を開き直し、指定項目を一つだけ変更して別名保存する。ケースを連続して編集した場合は、直前の保存ファイルを基準にして比較することを明記する。
5. レイヤーパネルの既定レイヤーは「なし」の場合がある。注釈作成前に検証者A/Bを選び、作成後は注釈のプロパティの「レイヤー」で所属を確認する。
6. 検証者Bにも注釈がある状態で独立性を検証するには、Bを既定にして矩形と短いタイプライター注釈を追加し、`baseline-ab.pdf` として保存する。その後はこのファイルを変更せず、各変種を作る。

評価版DEMOやURI Linkを削除しない。保存のたびに増えた場合は「レイヤーなし」の実際の変更として記録する。基準と変種のSHA256を記録する。注釈の作成者名はPDF記録値であり、実際の操作ユーザー・最終編集者を証明しない。

## ケースごとの操作と期待値

| ケース・保存名 | 実際に行う操作 | 期待する内容判定・確認事項 |
|---|---|---|
| A `a-resaved.pdf` | 基準を開き、編集せずCtrl+Shift+Sで新規名へ保存 | 内容が変わらなければ全グループ一致。DEMOが増えた場合はレイヤーなしだけ不一致も正常 |
| B `b-author.pdf` | コメント選択ツールで日本語注釈を選択。右クリック→プロパティ。右側「一般」の「作成者」をダブルクリックし、検証用の名前に変更してEnter。別名保存 | Aの内容は一致、作成者の名前別件数に変更あり。他レイヤーは一致。M等の保存日時や、DEMOの増加は別途調べる |
| C `c-text.pdf` | 基準を開き直す。日本語タイプライター注釈をダブルクリックして編集し、末尾のAだけをBに置換。Escで文字編集を終えて別名保存 | Aは不一致、BとPDF本体は一致。レイヤーなしはDEMO等の実際の変更に応じる |
| D `d-font.pdf` | 基準を開き直す。タイプライターの文字編集状態で注釈内の文字だけを全選択。「フォーマット」のフォント欄で、一覧にあるMSゴシックからMS明朝等へ変更。サイズ・色・文字列・注釈枠を維持して別名保存 | 安全に文字復元でき、非フォント属性が同じならフォントのみ変更の一致。復元不能なら検証不能も許容。Rect・AP内の配置等が変わった場合は「フォントだけの変種」と扱わず、実際の差を記録 |
| E1 `e-add.pdf` | Aを既定にして、矩形・矢印・チェックマーク等を1個追加。別名保存 | Aは不一致、他の未変更レイヤーは一致 |
| E2 `e-remove.pdf` | 基準を開き直し、Aの図形1個を選択してDelete。別名保存 | Aは不一致。作成者別件数も削除分を反映 |
| E3～E6 `e-move/resize/color/width.pdf` | 毎回基準を開き直す。矩形の移動、ハンドルによる拡縮、プロパティのストローク色、境界の幅を、それぞれ別ケースで変更 | 各ケースでAは不一致。位置と大きさなど、同時に変わった属性は記録する |
| F `f-order.pdf` | 基準の注釈を選び、右クリックの「整える」または「アレンジ」から前面／背面への移動を選ぶ。保存前後で注釈数・属性を維持 | 順序だけならAは一致。UI上で前後を変更できても、PDF内のAnnots配列や描画命令が実際に変わったかを別途解析する。変化がなければ「順序変更の検証成立」としない |
| G1 `g-a.pdf` / `g-b.pdf` | baseline-abから毎回開き直し、Aだけ、Bだけの文字または図形を変更 | 変更したレイヤーだけ不一致。Bにも実際に注釈がある状態で確認する |
| G2 `g-unlayered.pdf` | 既定レイヤー「なし」で注釈を追加 | レイヤーなしは不一致、A/Bは一致 |
| G3 `g-added.pdf` / `g-removed.pdf` | レイヤーパネルのレイヤー追加で新名を作成。削除は別コピーから空の新規レイヤーを選択して実施 | 新規追加／削除が該当レイヤーに現れる。削除時に注釈を移動・削除する選択をした場合は、その内容変更も記録する |
| G4 `g-owner.pdf` | Aの注釈を選び、プロパティの「レイヤー」をBへ変更して別名保存 | A/Bの両方が不一致。名前別注釈件数も移動を反映する |
| H `h-normal/saveas/optimized/incremental.pdf` | コピーごとに通常保存、別名保存、利用可能ならファイルメニューの最適化保存を実施。増分保存は実際の保存設定とPDF内のPrev・xref追記を確認できる場合のみ分類 | 内容・構造が同じなら一致。最適化で外観・フォント・所属が変わった場合は差を調査。未対応構造なら検証不能。保存メニュー名だけで増分保存と断定しない |

## 比較と記録

`start.bat` でツールを起動し、基準を1番目、変種を2番目へ指定する。GUIの各行で内容判定・差異と「注釈の作成者名（PDF記録値）」を確認し、TXT / CSV / JSONを新しい検証フォルダーへ保存する。JSONはschema_version 3、font_changesとauthors_changedを確認する。

コマンドラインでも、例えば次のように比較できる。実行環境は通常のインストール済みPythonと手動配置vendorを使う。

```bat
start.bat --json --output "output\xchange-validation\新しいフォルダー\B-result.json" "output\xchange-validation\新しいフォルダー\baseline-ab.pdf" "output\xchange-validation\新しいフォルダー\b-author.pdf"
```

ケースごとに、使用ファイル名、アプリ版、実操作、保存方法、変更した属性、PDF内部で実際に変化した属性、期待値、実際の判定、合否、検証不能理由を記録する。作成者の実名は公開文書へ転記しない。最終的に元PDF・既存検証データのSHA256が開始時と同じことを確認する。

優先順は **B 作成者名だけ → D フォントだけ → G 両レイヤーに注釈がある独立性 → E 図形差 → F 順序 → H 保存方式**。Cの日本語変更とAの変更なし保存は既存または今回の実出力で確認済みだが、同じ基準条件で不足する点があれば追加する。
